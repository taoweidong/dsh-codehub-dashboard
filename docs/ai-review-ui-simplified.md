# MR AI 检视 → Issue · UI 简化方案（修订）

> 修订日期：2026-10-18  
> 依据：用户指令「简化页面设计，不要求显示所有 MR 详情，详情跳转到对应页面；插件只显示标题和连接；重点是 MR 自动检视、列出结果、支持审查与自动创建检视意见；Issue 支持快速开始系统开发」  
> 配套文档：`ai-review-to-issue-design.md`（原设计稿）、`ai-review-to-issue-optimization.md`（后端缺口分析）  
> 结论：**本修订只改前端范围，后端设计（含优化文档的三处缺口）完全不变。**

## 1. 新的 UX 原则

插件定位从「GitHub 详情内联查看器」改为「**列表 + 执行**」面板：

1. **MR 列表**：每行只显示 标题（链接到 GitHub PR）+ 状态/CI 徽章 + 仓库 + 一个动作（AI 检视）。**不内联 diff、不内联完整 PR 元数据**。详情一律 `[在 GitHub 查看 ↗]` 跳转。
2. **MR 自动检视是核心**：一个入口触发 → 列出检视结果（findings）。
3. **支持审查**：每条 finding 可勾选「是否提 Issue」；默认按严重度预选（沿用原设计 5.4）。
4. **自动创建检视意见**：选中项一次批量创建 GitHub Issue（沿用原设计 `review.issues.create`）。
5. **Issue 快速开始系统开发**：在每个 Issue 行暴露「快速开始开发」按钮 → 复用**已存在**的 `issue.develop`（`workflows.js:450`，路由 `index.js:1222`）。无需新后端。

## 2. 为什么这样简化是安全的

| 原设计假设 | 代码事实 | 简化后 |
|------------|----------|--------|
| 前端内联展示 diff 网格（5.3 左栏） | diff 由服务端 `getPullRequest(repoKey, number, { diff: true })` 取给模型（`workflows.js:338`），前端从不需持有 diff | **删除前端 diff 渲染**；模型照常看 diff，用户不看 |
| 抽屉展示完整 PR 元数据 + 变更文件 | `mr`/`diff`/`files` 仅用于服务端快照与核验（`reviewSnapshot`，`workflows.js:97`） | 前端只取 `title`/`state`/`url` 等少量字段做标题+链接+徽章 |
| Issue 开发需新做 | `issue.develop` 已实现并接线 | 仅把按钮暴露到 Issue 列表行 |

## 3. 简化后线框（替代原 5.3 线框）

```
┌─ MR 列表 ───────────────────────────────────────────────┐
│ 筛选：☑ 待我评审 · 搜索[……]                              │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ [开放][CI✓] Fix crash in login        org/repo #123  │ │
│ │   作者 Alice · feat/a → main                       │ │
│ │ [AI 检视此 MR]              [在 GitHub 查看 ↗]       │ │
│ │                                                      │ │
│ │ AI 检视发现 4 个问题（覆盖完整）                       │ │
│ │ ▸ [阻塞] 空指针解引用  src/a.js:42 · 高置信 · 已核对 ☑ │ │
│ │ ▸ [重要] 连接未释放    src/db.js:118 · 中 · 未命中  ☑ │ │
│ │ ▸ [建议] 命名可读性    src/util.js:9 · 低          ☐ │ │
│ │ 已选 2/4              [创建 2 个 Issue]               │ │
│ └──────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────┘

┌─ Issue 列表 ─────────────────────────────────────────────┐
│ ┌──────────────────────────────────────────────────────┐ │
│ │ [开放] 空指针解引用  org/repo #128   [快速开始开发]   │ │
│ └──────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

- 问题卡片即主交互区，紧跟 MR 行；不再有「diff 下方通栏」与「右栏评论草稿」的二分。
- 评论草稿（可发布 COMMENT）降为 findings 下方的可折叠项（沿用 `review.publish`），不是主流程必选项。

## 4. 与原设计文档的差异表

| 原设计（5.3 / 5.4 / 5.6） | 简化后 | 影响 |
|---------------------------|--------|------|
| 抽屉内联 diff 网格（左栏） | 删除 | 少做一整块渲染 + diff 截断展示 |
| 抽屉展示完整 PR 元数据 + 变更文件列表 | 仅标题 + 状态徽章 + GitHub ↗ 链接 | 少做详情布局 |
| 评论草稿在右栏主区可编辑 | 折叠为 findings 下附属项 | 保留能力、降低视觉权重 |
| 问题卡片放 diff 下方通栏 | 问题卡片即 MR 行主区 | 布局简化 |
| MR 详情抽屉 + 关闭/重开恢复 | MR **行**内联结果 + `review.latest` 恢复 | 恢复逻辑不变，承载容器从抽屉变行 |
| Issue 开发需新做入口 | 复用 `issue.develop`，Issue 行加按钮 | **零后端新增** |

## 5. 保留不变的部分

- 一次模型调用、结构化降级、状态机、`unknown` 不重试、核验三态、覆盖受限提示 —— 全部不变。
- 我的优化文档三处后台缺口（4xx `preserveStatus` 双路径、96KB/32KB 双层上限、generating 锁时机）**不受影响**，照常落地。
- `review.latest` 恢复、`generating` 轮询、默认勾选规则、批量上限 10 —— 不变，只是渲染容器简化。

## 6. 对实施计划的影响

| Phase | 变化 |
|-------|------|
| Phase 0 | 不变（`review.latest`、generating 锁、客户端超时） |
| Phase 1 | 不变（解析、双层上限、system prompt） |
| Phase 2（UI） | **工作量显著下降**：删除 inline diff 渲染与 PR 元数据布局；重点改为「MR 行 + findings 列表 + 批量创建 + 恢复」；另加 Issue 行的「快速开始开发」按钮（薄封装 `issue.develop`） |
| Phase 3 | 文档同步：设计稿 5.3/5.4/5.6 按本修订改写；README 功能描述改为「列表 + AI 检视 + 批量建 Issue + 快速开发」 |

**净效果**：前端复杂度降低约一半，后端与正确性约束零变化；核心用户价值（自动检视 → 可审查 → 一键建 Issue → 一键开发）反而更突出。
